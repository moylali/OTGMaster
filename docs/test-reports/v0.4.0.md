# v0.4.0 (versionCode 46) — regression report

Required by `CLAUDE.md` rule 3. Every run is adb-driven (MainActivity in the
foreground, so remounts genuinely happen) and recorded in full in
[`../BENCHMARK_RUNS.md`](../BENCHMARK_RUNS.md), which is the source for every
figure here.

## Build under test

The release-candidate runs below were made on builds `5bc20eb` … `eb4ff66`. Every
commit in that range after `9169206` is either documentation or `7b5e3bb`, which
changes only the programmatic mount request the benchmark runner uses (it now
remounts plain partitions too). The user-facing code is the same across all of
them. Each report carries its own `build: … commit` line; none is `-dirty`.

What the release contains beyond v0.3.12, and so what these runs exercise:
LUKS1/LUKS2, ext4 read/write, per-partition read-only mode, the ext4
`needs_recovery` guard, the USB connection fix for mixed drives, and libaums
V8–V13 (FAT chain containment, FAT mirroring, card-reader unit attention, retry
buffer position, reset recovery, native clear-halt).

## What every run checks

- **write verify** — 16 MiB of position-dependent content, verified as written,
  after dropping every cached line, and after a proven unmount/remount.
- **unaligned** A (sector tail), B (truncate + rewrite), judged after a remount.
- **correctness** A–G — neighbour integrity, victim tail, unaligned
  offset+length, 100 odd-sized appends, recycled clusters, slack leak and read
  past EOF, read-only open writes nothing, 2 GiB file probes.
- **fixtures** — the drive's files against hashes computed on the host when it
  was prepared.
- **Host check afterwards** — the filesystem's own checker (`e2fsck -fn`,
  `fsck.exfat`, `fsck.fat -n`) through the kernel's drivers, and a full
  `volume_baseline.sh compare` of every file and the allocation tables.

## Not covered

- **Samsung M30: VeraCrypt + ext4 and plain ext4** — never run.
- **OnePlus 7: LUKS1 + ext4** — only an early run, before the ext4 metadata fixes.
- **Plain partitions on phones whose Android mounts them itself** (OnePlus 7,
  Android 16): the app opens such a partition read-only when Android's mount was
  cut off (`needs_recovery`), so its write path cannot be exercised there without
  a host `e2fsck` first. Handled by the read-only guard, not a pass.

## Known limitations shipping in this release

- **Unplugging an exFAT drive while writing can damage it.** libexfat writes the
  allocation bitmap only at flush, after the entries that reference it. Seen once
  (Samsung, an adapter dropping mid-mkdir), repaired with `fsck.exfat`. In the
  README and the release notes.
- **Android may mount plain partitions itself** before the app opens the drive;
  such an ext4 partition then opens read-only (the `needs_recovery` guard).
