# v0.4.1 (versionCode 47) — regression report

Required by `AGENTS.md` rule 3: at least three devices. The three are the OnePlus 7, the
Pixel 7 Pro and the Samsung M30, each run on all four matrix drives on the release code;
the Huawei P20 Lite's earlier, partial run is reported but not counted. Every run is

## Build under test

The release is `main` at `d330a32` (branch hash `a5f10ae`). The runs below used four builds;
their **app** code differs in one place only:

| Build | App code relative to the release | Benchmark harness |
|---|---|---|
| `8655eeb`, `2a6fe4f` | the release **minus the exFAT delete-leak fix** (`ExFatNative.cpp` `deleteNode`) | as merged in #31 |
| `cfc9a64` (main `eecf254`) | the same as above | + waits for unlocks in progress, counts the old tree as free |
| `a5f10ae` (main `d330a32`) | **the release** | as cfc9a64 |
| `ae25575` | the release | + saves `benchmark-in-progress.txt` after every partition |

So results on the earlier builds stand for everything except exFAT deletes, and every exFAT
partition was re-run on `a5f10ae` / `ae25575`. Each report carries its own `build: … commit`
line; none is `-dirty`.

What 0.4.1 adds over 0.4.0, and so what these runs exercise: NTFS read/write (plain, VeraCrypt,
LUKS, BitLocker); BitLocker by password or recovery key; Mac APFS read-only, plain and
encrypted; LUKS2 4K sectors; ext2/ext3 read-only; the ext4 delete-ordering fix (#33); libaums
V14–V18 (FAT32 allocation bound, moves, empty files, listing under GC, small volumes); exFAT
volume labels; the USB transfer-size fallback (#29) and the "why no USB device" hints; the
Android 10 shortcut/password fix; and the exFAT delete-leak fix (PR #37).

## What every run checks

- **On the phone:** block layer, listing (10,000-entry directories), path resolution,
  sequential and random read, opens; **write verify** (16 MiB, verified as written, after
  dropping the cache, and after a remount); **unaligned** A+B; **correctness** A–G;
  **bigwrite** — a 2.2 GB keystream file in odd-sized chunks past 2³¹, and a 250-file tree put
  through create / overwrite / append / truncate / rename / move / delete, both re-verified
  after a remount; **fixtures** — every file on the drive (≈21,000) against hashes computed on
  the host. ext2/ext3/APFS skip the write sections by design.
- **On the laptop afterwards**, every drive, every run: `verify_matrix_drive.py` — independent
  decryption, each filesystem's own checker, a chunk-by-chunk compare against the build
  baseline, every bigwrite file against its recipe, and exFAT space no file owns.

## Not covered

- **The Samsung M30's USB link on Drive 2.** Four attempts on 10-07 and 10-09 ended with
  the link dropping (`MAX_RECOVERY_ATTEMPTS`, transfers already at 16 KiB). Run one
  partition at a time on 10-10 it completed every partition; the drops did not recur.
- **The Pixel 7 Pro on a hub or direct adapter under long runs.** Three USB drops in a day,
  each taking every device on the bus at once; the runs that completed are above.
- **Huawei P20 Lite** beyond Drive 4 on `8655eeb`; not counted toward the three devices.

## Known limitations shipping in this release

- **Android may mount a FAT32 partition itself** (Samsung, Android 10): when the app releases
  the drive, Samsung's Android can mount it; pulling the stick then leaves the FAT32 dirty
  flag set and the free count off by one. Files are intact; a desktop `fsck` repairs it. Seen
  twice on the M30's D1FAT32; drives unplugged while the app still held them came back clean.
- **Interrupted writes are not journalled.** A drive pulled mid-write can leave orphaned FAT32
  clusters or an ext4 extent past the file size — repaired by the OS's checker, seen in the
  hub-drop and USB-drop runs above.
- **Write speed:** ext4 (≈0.6–1.2 MB/s) and exFAT (≈0.7–1.6 MB/s) write 3–7× slower than FAT32
  on the same phone (#36, and a follow-up for exFAT).
- **Read-only:** ext2, ext3 and APFS.
- **VeraCrypt:** AES and Serpent with SHA-512 only; no cascades, no other PRFs, no Argon2id.
