# v0.5.3 (versionCode 52): regression report

`AGENTS.md` commit rule 3 asks for at least four devices. **The owner waived that for this tag**
(2026-11-16). Three devices ran the full device matrix, all five drives with bigwrite: a Pixel 7
Pro, a OnePlus 7 and a Galaxy Tab A9+. Unlike 0.5.2, this release changes filesystem and I/O code
(FAT32, exFAT, the block cache and the DocumentsProvider), so every run had the bigwrite section on
and every drive was read back and checked on the laptop. Every run is recorded in full in
[`../BENCHMARK_RUNS.md`](../BENCHMARK_RUNS.md) ("2026-11-12 to 11-16: the 0.5.3 release matrix on
`20b582c`"), and every figure here comes from there.

## Build under test

All three devices ran `0.5.3-bench (52) commit 20b582c`, the benchmark build type
(release-optimised and minified, package `app.fayaz.otgmaster.bench`). `20b582c` is `main` after
#151 and its hash-table PR #152. The tagged tree adds only this report, the run log and the store
screenshots.

What the release adds since v0.5.2 (#151, all findings of three reviews, each with a test that
fails on the old code):

- "Use backup header" on the unlock form opens a VeraCrypt volume whose main header is damaged.
- A hidden volume gets its own drive id, so an app given access to the outer volume cannot read it.
- FAT32: a file that grows has the exposed clusters zeroed (deleted data was readable); files past
  4 GiB are refused instead of truncated; a looping cluster chain ends instead of exhausting memory.
- Block cache: a hit is copied under the lock, so an eviction cannot zero a read in progress.
- DocumentsProvider: opens are resolved under the drive lock; a file left open across Format or
  Encrypt cannot write to the new volume.
- exFAT: a failed metadata flush reports an error instead of success.
- Backups and restores: a plain copy's manifest never replaces a copied file; keep rules never delete
  the last complete or the restoring snapshot; restore writes to a hidden file first and honours
  Cancel.
- VeraCrypt and LUKS2: headers the app cannot use are refused; keyfiles fail closed; the PIM is not
  logged; LUKS2 digests, bounds and both header copies are checked; an Argon2i keyslot is derived
  with Argon2i; key material is wiped after use.
- GPT counts are checked before they size a read; every volume of an APFS container can be opened.
- A waiting Unmount or Eject acts after 5 s of continuous quiet and survives the activity.
- The benchmark and debug receivers accept broadcasts from adb only.

## What every run checks

free, block, dir, path, seq, random, opens, write verify, unaligned, correctness and fixtures, and
bigwrite (a 2.2 GB file plus a tree of about 250 files), except on D5 p7 to p10 (below). After
every drive the laptop runs each partition's own checker read-only, matches every fixture against
the manifest and compares the volume with its baseline. Every sequence ends by ejecting the drive
in the app.

## Results

Partitions that passed, out of ten per drive:

| | Drive 1 | Drive 2/2 | Drive 3 | Drive 4 | Drive 5 |
|---|---|---|---|---|---|
| Pixel 7 Pro | 10/10 | 10/10 | 10/10 | 10/10 | 10/10¹ |
| OnePlus 7 | 10/10 | 10/10 | 10/10 | 10/10 | 10/10¹ |
| Galaxy Tab A9+ | 10/10² | 10/10² | 10/10² | 10/10 | 10/10¹ |

Read-only partitions (APFS, ext2, ext3) run the read sections and fixtures and skip writes by
design. Every other partition passed write verify, unaligned, correctness and bigwrite and matched
all of its fixtures.

1. **D5 p7 to p10 ran without bigwrite.** On those 2 GiB partitions exFAT uses 32 KiB clusters, and
   the 20,000 fixture files leave about 95 MB free, so the bigwrite tree hits ENOSPC (-28). The
   first attempts on the Pixel (`px-053b`, `px-053c`) and the Tab (`tab-053c`) failed there with
   `exFAT write failed at offset 0 ... -28`, recorded as results. A script bug (`MATRIX_TESTS`
   overriding the "no bigwrite" setting for those partitions) had put bigwrite back; the reruns
   with it off passed. Those four partitions have no large-write result on any device.
2. **Tab results come from several sequences** because of USB failures (next section).

### Galaxy Tab A9+ USB failures, and the 0.4.2 comparison

The Tab stopped a sequence on a USB failure seven times, each time in a big write: `D2BLFAT32`
(`tab-053a`), `D1EXFAT` (`tab-053b`), `D3L1EXFAT` (`tab-053d`), `D3L2FAT32` (`tab-053e`),
`D1EXT4` (`tab-053g`), `D3L2NTFS` (`tab-053h`) and `D3L2EXT4` (`tab-053l`). Each began with
libaums giving up on a bulk transfer (`MAX_RECOVERY_ATTEMPTS Exceeded`), then `EIO (-5)` or
`could not write the last N KiB again after a failed write`. Each partition passed on a rerun in a
later sequence. The Pixel and the OnePlus, on the same build and the same sticks, had no USB write
failure (OnePlus 0 recovery errors, Pixel 3, all recovered).

On 0.4.2 (`cae0e9e`, 11-04) the Tab had passed bigwrite on 32 of 32 partitions. To find out whether
0.5.3 caused the failures, the same 0.4.2 APK was installed on the Tab on 11-16 and run on Drive 1
with the same hub and cable (`tab-042ab`). It failed the same way: D1FAT32 and D1EXFAT passed, then
D1NTFS's bigwrite hit `MAX_RECOVERY_ATTEMPTS` and `NTFS write ... failed: I/O error (EIO)` at
711 MB. The USB transport code (`LibaumsRawBlockDevice` and libaums' SCSI and USB driver) is
byte-identical between `cae0e9e` and `20b582c`, and the Tab's Android build (2026-08-05 patch) is
the same for both. **The failures come from the Tab's USB link, not from 0.5.3.** The cause on the
Tab side (hub, cable, port or power) is not identified.

3. **`D3L2EXT4`:** `e2fsck -fn` reports `Block bitmap differences: -(879218--879407)`. Every file's
   contents match. `Ext4File.write` marks new blocks in the bitmap at once and writes the inode only
   at the end, so a write that dies part-way (the Tab's USB failure) leaves blocks marked used with
   no owner. `Ext4WriteFsckTest` reproduces it on this code; the fix rolls back the blocks past the
   old end of file on a failed write and is **not in 0.5.3** (filed for 0.5.4). **Known issue in
   this release:** an interrupted write to an ext4 volume can strand free space until a Linux
   `fsck` repairs it. No file data is lost. `D3L2FAT32`'s stray file was left by an `fsck.fat`
   repair on the laptop, not by a run.
4. The FAT32 dirty bit is set when Android (vold) mounts a plain FAT32 partition while the app does
   not hold the drive; `matrix/helpers/start_run.sh` unmounts Android's volumes before a run.

## Baseline comparisons

Every partition that took writes differs from its baseline in its allocation tables, as expected
after runs that write and delete files, and on some exFAT partitions the boot sector's
PercentInUse byte differs, which follows the fill level. These differences were not judged entry
by entry against what each run should have changed, as the 0.5.2 report did; the checker and the
full fixture match above are what this report relies on.
