# v0.5.2 (versionCode 51): regression report

`AGENTS.md` commit rule 3 asks for at least four devices. **The owner waived that for this tag**
("so we can skip 4 device testing"), because 0.5.2 changes no filesystem or I/O code: nothing in
FAT32, exFAT, NTFS, ext4 or APFS, the block cache, libaums, libexfat or the DocumentsProvider's
read and write path changed since v0.5.1. One phone, the OnePlus 7, ran all five matrix drives on
the release-optimised benchmark build, and **the bigwrite section was left out**, so no run here
exercises large writes. The Pixel 7 Pro and a Redmi 4 timed unlocks only. Every run is recorded in
full in [`../BENCHMARK_RUNS.md`](../BENCHMARK_RUNS.md) ("2026-11-09 to 11-11: 0.5.2 on the OnePlus
7, without bigwrite"), and every figure here comes from there.

## Build under test

Drives 2/2, 3, 4 and 5/1 ran `build: 0.5.2-bench (51) commit 0502f57`: `main` after #141 and its
hash table (#144), the benchmark build type (release-optimised and minified, package
`app.fayaz.otgmaster.bench`). The tagged tree differs from it only in docs and records.

Drive 1 ran `27523c9` (= `d7e3810` on `main`). The commits after it change two E2E tests and one
line of the Settings dialogs (`15ad245`: test tags exposed to UiAutomator, no visible change), so
Drive 1 was not rerun.

What the release adds since v0.5.1:

- A mount request tries every standard VeraCrypt header before any hidden one, so a request on a
  drive with several locked partitions runs one key derivation per partition again (0.5.1 ran a
  hidden-header try after each failed standard one: 11 derivations instead of 6 on Drive 5/1).
- Argon2's `fill_block` in NEON on arm64, from upstream's SSE code: same keys as the reference
  code (RFC 9106 vector), about 1.3x faster.
- Unmount waits for an open file or a running backup to finish, as Eject does.
- The Donate dialog shows Ko-fi's button and links to the site's Support section.
- A hint at the Drives icon (with "Don't show again"), and the mounted-drives notification opens
  the slider.

## What every OnePlus run checks

free, block, dir, path, seq, random, opens, write verify, unaligned, correctness and fixtures, as
in [`v0.5.0.md`](v0.5.0.md). Not bigwrite. After every drive, the laptop runs each partition's own
checker read-only, matches every fixture against the manifest, and compares the volume with its
baseline. From Drive 2/2 on, each sequence ends by ejecting the drive in the app.

## Results

| | Drive 1 | Drive 2/2 | Drive 3 | Drive 4 | Drive 5/1 |
|---|---|---|---|---|---|
| OnePlus 7 | 10/10 · CLEAN | 10/10 · CLEAN | 10/10 · CLEAN¹ | 10/10 · CLEAN | 10/10 · CLEAN² |

The read-only partitions (APFS, ext2 and ext3) run the read sections and fixtures, and skip the
writes by design. Every other partition passed write verify, unaligned and correctness, and every
partition matched all of its fixtures.

1. **D3EXT2 and D3EXT3, plain ext2 and ext3: Android wrote their superblocks.** Android's vold
   mounts plain ext partitions read-write when the drive is attached (11-11 05:56, before the run)
   and again the moment the app's Eject released the drive (06:51:57). Only the first MiB, the
   superblock (mount time, mount count, state), differs from the baseline; the checker is clean
   and every fixture matched. The app only ever reads these partitions. Accepted by the owner and
   recorded in `matrix/accepted-052.json`; the baselines now hold the current superblock.
2. **Drive 5/1 on `0502f57`:** fsck clean on all ten, including p8 and p9 (plain FAT32), which
   came back with Android's dirty bit after the `op-052a` run on 11-09; every fixture matched. The
   allocation tables differ from the October baseline by what earlier runs left (p1's FAT by
   1785736 bytes, against 1785703 after the 0.5.1 round), a few bytes more per run.

Two runs produced no result and were rerun: D1EXFAT in `op-052b` (stopped by the ext4 Repair
prompt that vold's mount caused; rerun in `op-052c`, after `start_run.sh` began unmounting vold's
volumes before each run), and D2BLFAT32 in `op-052d` (the reinstall cleared the USB permission,
the prompt was answered after the mount request had given up; rerun as `op-052e`).
