# v0.4.2 (versionCode 48) — regression report

Required by `AGENTS.md` commit rule 3. Every run is adb-driven and recorded in full in
[`../BENCHMARK_RUNS.md`](../BENCHMARK_RUNS.md) ("the 0.4.2 release matrix on `6e281db`"), which is
the source for every figure here.

**Rule 3 asks for four devices; this report has three on the release build.** The fourth (the
realme 8, or another phone) will be run after the tag, on the user's decision: the release goes to
Play's internal track first and its rollout can be halted. This file is updated when that run is in.

## Build under test

Every report is stamped `build: 0.4.2 (48) commit 6e281db`. `6e281db` is PR #78's head; it landed
on `main` as `de98da6` with an identical tree, and `de98da6` is the code tagged — the commits after
it on `main` are documentation, store screenshots and this report.

What the release contains beyond v0.4.1, and so what these runs exercise: VeraCrypt Encrypt (with
keyfiles) and Format (FAT32/exFAT) of a mounted partition; VeraCrypt Twofish, the five cascades
and Argon2id; Serpent on the Linux kernel's bitsliced code (~140× faster); the FAT32 write runs
(V19) with the partial-sector tail fix (V21); drives over 1 TiB; video playback from the Files app;
reads of capacity and free space moved off the main thread (the Pixel ANR); the tablet two-pane
layout, the More actions menu, and the "OTG is switched off" hint on OPPO/realme/OnePlus.

## What every run checks

- **free, block, dir, path, seq, random, opens** — read paths and timings.
- **write verify** — 16 MiB of position-dependent content, verified as written, after dropping
  every cached line, and after a proven unmount/remount.
- **unaligned** A and B, **correctness** A–G (as in v0.4.0's report).
- **bigwrite** — a 2.2 GB file and a 245-file tree, read back after a remount.
- **fixtures** — every file of the partition's manifest against hashes computed on the host.
- Format/Encrypt targets: the app formats or encrypts the partition first, then the read
  sections and fixtures run on the result.
- **Host check afterwards** — each partition's own checker read-only through the kernel
  (`fsck.fat -n`, `fsck.exfat`, `e2fsck -fn`, an NTFS consistency check, `apfsck`), plus a byte compare of the
  fixtures (Drives 1–4: `verify_matrix_drive.py`; Drive 5: `verify_volume.sh` + manifest hashes).

## Results

Read-only partitions (APFS, ext2/ext3) run the read sections and fixtures; writes are skipped by
design.

| Pixel 7 Pro | 10/10 · host 9/10 CLEAN¹ | 10/10 · CLEAN | 10/10 · CLEAN | 10/10 · CLEAN | 10/10 · CLEAN |
| OnePlus 7 | 10/10 · CLEAN | 10/10 · CLEAN | 10/10 · CLEAN | 10/10 · CLEAN | 10/10 · CLEAN |
| Samsung M30 | 10/10 · CLEAN | 10/10 · CLEAN | 10/10² · CLEAN | — | **FAILED**³ |

Big-write throughput (2.2 GB, MB/s write / read-back after remount), the range across the
writable partitions of Drives 1–4: Pixel 2.6–9.4 / 25–42; OnePlus 2.6–8.9 / 13–27; M30 1.9–5.7 / 8.7–19
(Drive 5's cascades, write: Pixel 2.6–4.8, OnePlus 2.6–3.9, M30 1.1–2.1).

1. **D1FAT32 after the Pixel:** dirty flag set, free-cluster count off by one; all fixtures and the
   big write matched. The Pixel's vold mounts a plain FAT32 partition itself with the kernel vfat
   driver when the drive is attached, and the drive was pulled with that mount up. Clean after the
   OnePlus and M30 runs, which do not auto-mount it. Repaired with `fsck.fat -a`.
2. **Drive 3 on the M30:** D3L1EXFAT and D3L4EXFAT lost the stick mid-write (USB, below) and passed
   on rerun; the host check after both is CLEAN.
3. **Drive 5 on the M30:** two partitions passed (VC_ATS_ARGON_PIM0, VC_STA_ARGON_PIM1); six
   attempts failed when the stick stopped answering USB transfers. The stick stays enumerated but
   ignores Reset Recovery until replugged. The same build and sticks pass all ten partitions on the
   other two phones, and Drives 1 and 2 pass on the M30, so this is recorded as an M30 + PNY-stick
   link problem rather than a regression; a full USB reset as the next recovery step is planned
   for 0.4.3. Two cut-off writes left damage the host checker found — NTFS `$Bitmap` behind the
   MFT (…EF455 p3) and a stale FAT32 FSInfo count (…EF449 p1); both restored. **Not yet
   host-checked:** …EF455 p4 and …EF449 p1 after the last two dropouts.
