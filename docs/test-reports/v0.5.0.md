# v0.5.0 (versionCode 49): regression report

Required by `AGENTS.md` commit rule 3, which asks for at least three devices. Three phones ran
the full matrix on the release build. Every run was driven over adb and is recorded in full in
[`../BENCHMARK_RUNS.md`](../BENCHMARK_RUNS.md) ("the 0.5.0 release matrix on `cae0e9e`"). Every
figure here comes from there.

## Build under test

Every report is stamped `build: 0.4.2 (49) commit cae0e9e`. `cae0e9e` is PR #117's head, and it
landed on `main` as `d0e5655` with the same files. The tagged tree differs from it by one line,
versionName `0.4.2` → `0.5.0` (`4782c56`), plus store screenshots and records. The Settings drawer
is the only place the name shows.

What the release adds since v0.4.2, and so what these runs exercise: backups between a phone and a
drive (restic repositories, schedules, reminders, mounting a backup); recovering deleted files on
FAT32 and exFAT; another phone or camera over USB as a read-only drive; Format and Encrypt
writing ext4 and NTFS, and Encrypt creating LUKS2; the slider for mounted drives and backups; the
last 1 MiB written again after any USB reset (libaums V25); drives over 2 TiB; drives plugged in
at the lock screen; folder delete on ext4 and exFAT, safe on hard links.

## What every run checks

- **free, block, dir, path, seq, random, opens**: read paths and timings.
- **write verify**: 16 MiB of position-dependent content, verified as written, after dropping
  every cached line, and after a proven unmount and remount.
- **unaligned** A and B, **correctness** A to G (as in v0.4.0's report).
- **bigwrite**: a 2.2 GB file and a tree of about 245 files, read back after a remount. Not run on
  Drive 5's 2 GiB partitions, which are too small.
- **fixtures**: every file of the partition's manifest against hashes computed on the host.
- **Host check afterwards**, on the laptop, after every phone's run of every drive: each partition's
  own checker, read-only (`fsck.fat -n`, `fsck.exfat`, `e2fsck -fn`, an NTFS consistency check,
  `apfsck`), every fixture against the manifest, the chunk baseline, and big.bin and the tree
  against the bigwrite keystream (Drives 1 to 4: `verify_matrix_drive.py`). Drive 5:
  `verify_volume.sh`, manifest hashes and `volume_baseline.sh compare --metadata-only`.

## Results

The read-only partitions (APFS, ext2 and ext3) run the read sections and fixtures, and skip the
writes by design.

| | Drive 1 | Drive 2 | Drive 3 | Drive 4 | Drive 5 |
|---|---|---|---|---|---|
| OnePlus 7 | 10/10 · CLEAN | 10/10 · CLEAN (Drive 2/2)¹ | 10/10 · CLEAN | 10/10 · CLEAN | 10/10 · CLEAN |
| Galaxy Tab A9+ | 10/10 · host 9/10² | 10/10 · host 9/10³ | 10/10 · CLEAN | 10/10 · CLEAN | 10/10 · host 8/10² |
| Pixel 7 Pro | 10/10 · CLEAN | **9/10** · host 9/10¹ | 10/10 · CLEAN | 10/10 · CLEAN | 10/10 · host 8/10² |

Big-write throughput (2.2 GB, MB/s write / read-back after remount), the range across the writable
partitions of Drives 1 to 4: OnePlus 2.7–8.8 / 13–26; Tab A9+ 2.0–6.1 / 10–20; Pixel 2.7–9.3 / 25–41.
Drive 5's cascades, write: OnePlus 2.6–4.4, Tab A9+ 2.0–3.5, Pixel 2.5–5.2.

Every cell that is not CLEAN has an explained cause that is not app damage, and the user accepted
each one on 11-07:

1. **The original Drive 2 stick loses 16 KiB flash pages.** Pixel, D2VCNTFS: bigwrite FAILED,
   `big.bin` differs at byte 341196800 after remount; fsck clean, every fixture and the tree
   matched. The stored encrypted bytes are a 16 KiB run of 0x55 with correct sectors either side.
   The expected data is nowhere else on the partition, no XTS tweak nearby explains it, and no app
   code writes that fill. The same stick lost a page on the OnePlus in D2BLFAT32 (found by the
   laptop; the phone's read after remount had matched), on a different container and filesystem.
   No other stick has shown it. The stick was retired, and the OnePlus ran Drive 2 again on Drive
   2/2 on the same build: 10 of 10, ALL CLEAN. This diagnosis is not proven by a surface test.
2. **Android's vold sets the FAT32 dirty bit** (Tab D1FAT32, Tab and Pixel Drive 5 p8 and p9, all
   plain FAT32). Proven on the tablet with the app disabled: vold mounts every plain FAT32 and
   exFAT partition at plug-in, the kernel's vfat driver sets boot-sector byte 0x41, and unplugging
   with those volumes mounted leaves it set. Only the dirty bit and FSInfo differ; every fixture and
   the big write matched. Running `sm unmount` before unplugging avoids it.
3. **A stray file** on Drive 2's D2VCEXFAT, `BENCH/file with spaces.txt`, copied there by hand
   on 10-30, not by any run (also seen after the OnePlus run on the old stick). Deleted.
