# v0.5.4 (versionCode 53): regression report

`AGENTS.md` commit rule 3 asks for at least four devices. **Three devices ran, so this report does
not meet that rule as written**: a Pixel 7 Pro, a OnePlus 7 and a Galaxy Tab A9+, each on all five
drives with bigwrite. The owner waived the fourth device for this tag on 11-24: three devices are enough for 0.5.4. This release changes the USB write replay, the ext4 and
FAT32 write paths and the DocumentsProvider, so every run had bigwrite on and every drive was read
back and checked on the laptop after every device. Every run is recorded in full in
[`../BENCHMARK_RUNS.md`](../BENCHMARK_RUNS.md) (the 0.5.4 sections dated 11-19 to 11-24), and every
figure here comes from there.

## Build under test

`0.5.4-bench (53)`, the benchmark build type (release-optimised and minified, package
`app.fayaz.otgmaster.bench`). Eleven of the fifteen device and drive pairs ran entirely on
`b5c79aa`, the head of PR #186 (`fix/provider-roots-anr`). The rest ran earlier commits of the
same branch, and the owner accepted them for the tag because the later commits do not touch the
filesystem code:

| Device and drive | Build | What `b5c79aa` adds on top |
|---|---|---|
| Galaxy Tab A9+, D1 and D2/2's first six partitions | `b65821c` | `068d7c7` USB replay, `475972e` and `959ac22` provider |
| Galaxy Tab A9+, D2/2's last four partitions | `ccfa3c7` | `959ac22` provider |
| OnePlus 7, D5/1 p1 to p3 | `b65821c` | as above |
| OnePlus 7, D5/1 p4 to p10 | `475972e` | `959ac22` provider |
| OnePlus 7, D1FAT32 | `959ac22-dirty` | nothing in the app (the dirty files were `b5c79aa`'s test data) |

D2L2EXFAT, the Tab partition whose `b65821c` run failed (below), was run again on `ccfa3c7`, which
has the fix.

The tagged commit adds to `b5c79aa` (`deb26e0` on `main`) only the Brazilian Portuguese translation
(#177: string resources, no code) and docs. The Format inside BitLocker run below used `4839137`,
`main` with both merged.

What the release adds since v0.5.3:

- Saved drive passwords open only within 30 s of the phone's lock; Auto mount says it needs a
  screen lock. Read-only mode covers plain drives.
- BitLocker: Format inside a BitLocker volume, and unlock with a `.BEK` key file.
- The app says when taking a drive cut Android off mid-use.
- Feedback reports: the log can be edited before sending, file and folder names in it are masked,
  and nothing reaches the server before Submit.
- USB: a failed write in the replay after a reset is recovered, and the replay now also rewrites
  the blocks of the flash unit before its window (`068d7c7`, found by this matrix, below).
- ext4: a write that fails part-way no longer leaves blocks marked used with no owner (the 0.5.3
  known issue).
- A full drive says "Not enough space"; a FAT32 card whose FSInfo has no free count no longer shows
  0 B free.
- The drive list and the Files app's queries no longer wait on a busy volume (the ANRs, below).
- Format inside a BitLocker volume (`efd963e`), checked on hardware below.
- Brazilian Portuguese (#177, from a contributor).
- Privacy and key handling: other apps see drives only through the standard DocumentsProvider
  columns, and native copies of master keys and passwords are wiped.

## What every run checks

free, block, dir, path, seq, random, opens, write verify, unaligned, correctness and fixtures, and
bigwrite (a 2.2 GB file plus a tree of about 250 files, the tree skipped where the partition cannot
hold it), except on D5/1 p7 to p10, which run without bigwrite. From `ccfa3c7` on, bigwrite also
queries the app's own drive list once a second and reports the slowest answer. After every drive
the laptop runs each partition's own checker read-only, matches every fixture against the manifest
and compares each read-only partition with its build image. Every sequence ends with the app's
Eject.

## Results

Partitions that passed, out of ten per drive:

| | Drive 1 | Drive 2/2 | Drive 3 | Drive 4 | Drive 5/1 |
|---|---|---|---|---|---|
| Pixel 7 Pro | 10/10¹ | 10/10 | 10/10² | 10/10 | 10/10 |
| OnePlus 7 | 10/10 | 10/10 | 10/10² | 10/10 | 10/10¹ |
| Galaxy Tab A9+ | 10/10 | 10/10³ | 10/10 | 10/10 | 10/10 |

Read-only partitions (APFS, ext2, ext3) run the read sections and fixtures and skip writes by
design. Every other partition passed write verify, unaligned, correctness and bigwrite, matched all
of its fixtures, and checked clean on the laptop, except as noted.

1. **FAT32 dirty flag set by Android, not by the app.** Pixel D1FAT32 and OnePlus D5/1 p8 and p9
   (plain FAT32) failed `fsck.fat` on the dirty flag (boot sector byte 0x41) and on nothing else.
   Every file matched and `big.bin` matched its keystream. Android mounted these plain partitions
   after the app's Eject, which is what sets the flag. The owner accepted these: no data was wrong.
2. **D3EXT2 and D3EXT3: 1 MiB changed on partitions the app never writes.** After the OnePlus
   run, both superblocks read last mount 11-22 22:14:00 and mount count 1: Android's vold mounted
   them when the app released the drive at the 22:14 Eject. `e2fsck` was clean and every fixture
   matched. The Pixel's later run shows the same 1 MiB with the same timestamps, so the Pixel did
   not write them. The owner accepted these. They were not restored.
3. **D2L2EXFAT on `b65821c` failed bigwrite, and found a bug.** `big.bin` read back after the
   remount differed at byte 1,443,520,512. A read had needed a USB reset, and the replay wrote the
   last 904 KiB again from block 77,716,137. The laptop found exactly one wrong 512-byte sector,
   device sector 77,716,136, the one just before the replay window and in the same 4 KiB unit.
   exFAT's fsck was clean and all 20,942 fixtures matched, so only the keystream check could see
   it. `068d7c7` now also rewrites the start of the oldest write's 64 KiB unit; `WriteReplayTest`
   has two new cases that fail on the old code at that block. D2L2EXFAT then passed on `ccfa3c7`
   on the Tab and on `b5c79aa` on the OnePlus and the Pixel, and D2/2 checked ALL CLEAN after each.

## The drive-list ANR

On `b65821c` the Tab showed "not responding" twice: during D2L1FAT32 on 11-21 (the run still
passed) and while bigwrite deleted the old 2.2 GB `big.bin` on D3L1EXFAT on 11-22, where closing
the dialog killed the app mid-write (that run produced no result). Both traces show the provider's
drive list (`queryRoots`) waiting on the volume's lock. `475972e` reads free space on a worker with
a 500 ms wait, and `959ac22` bounds the Files app's other queries the same way.

Measured on the Tab, D2BLFAT32, bigwrite only:

| Build | Drive-list queries during bigwrite | Slowest | Over 1 s |
|---|---|---|---|
| `b362621` (control: the fix taken out) | 784 | 13,472 ms | 3 |
| `ccfa3c7` (fix) | 791 | 532 ms | 0 |

Across the 79 runs on the three devices that report it, 77 had no drive-list query over a second.
Two OnePlus 7 NTFS runs did: 24 of 614 queries over 1 s, slowest 1,019 ms (D1BLNTFS, `op7-054e`),
and 19 of 625, slowest 1,016 ms (D2VCNTFS, `op7-054g`). None came near the 13 s of the control.
Android reports an app not responding after 5 s. Why those queries took about a second is not
identified.

## Format inside BitLocker

On the OnePlus 7, build `4839137`, a full Format (every sector overwritten) of D1BLEXFAT, BitLocker
AES-XTS with exFAT inside, finished with "Formatted as exFAT and mounted." A 1 GiB file and a 300 KB
file of random data then copied onto it through the Files app. On the laptop, `cryptsetup` still
read the BitLocker header and both protectors. Decrypted with `bitlk_decrypt.py`, which shares no
code with the app, `fsck.exfat` was clean and both files matched the hashes taken on the phone.
D1BLNTFS next to it and the other partitions were unchanged; D1FAT32 had only Android's dirty flag¹.
D1BLEXFAT was restored from its build image and checked CLEAN. The benchmark run on the formatted
volume wrote nothing, by design, because the volume had no `BENCH/MANIFEST.txt`.
